---
name: progress-checker
description: Plan project milestones and report progress using the local Progress Checker tools. Use when setting up project tracking, recording implementation claims, checking verification, or explaining remaining work.
---

The plugin installs once globally. The 0.4 first-time setup uses Codex's native `/plugins` browser: Add marketplace `lwdot90/Progress-checker-for-Codex`, install **Progress Checker**, and start a new chat if requested. This is a custom Git marketplace, not a claim of universal directory listing. Publication and qualification of the 0.4 candidate remain pending; do not describe it as released or verified without current evidence. New users do not need the archive installer. Existing custom profile or state bindings require explicit migration; retain the same state location or continue the archive-managed entry.

When the user asks to track the current project, call `checker_track_project` with `project_root` set to the absolute Git worktree root of the current Codex session (use `git rev-parse --show-toplevel` in the session project if needed). The server starts in the plugin cache and cannot independently infer or attest the session root: never use the plugin cache, infer a root from another conversation, or select another repository. Confirm the returned `canonical_root` matches the intended project before submitting plans or claims, and retain the returned `state_directory` for any approval command. Tracking preserves existing configuration, creates an empty starter plan only when absent, and adds managed project instructions; it never approves or executes checks. No terminal installation is needed for additional projects.

A global connection stays bound to one project. Use a separate Codex session for another project. A `PROJECT_NOT_TRACKED` response means project activation is needed. A `PROJECT_ALREADY_BOUND` response requires a new session, not a retry with another path. Legacy project-bound installations do not expose the tracking tool: read their `checker_get_project` directly and confirm the root.

Read `checker_get_project` before changing a tracked project; confirm its canonical root, current revision, and configuration hash. Distinguish planned work, implementation claims, and current verification. Installation does not imply that a project has milestones or verified progress.

When planning, derive explicit outcomes and acceptance criteria from the user's requirements. Define the checks that establish each criterion and any milestone dependencies. Show scope changes explicitly; never remove unfinished requirements silently to reach 100%. Submit the accepted complete configuration through `checker_submit_plan`, supplying the revision and config hash from `checker_get_project` plus a reason. Read scope changes with `checker_get_plan_history`; retain unchanged requirements. Changed milestone definitions reset their implementation claims, and plan revisions invalidate execution approvals.

Read the current revision before `checker_set_claim`. Mark work implemented when its changes exist, then use `checker_get_progress` for verification. A queued check or implementation claim is not passing evidence. Changed files can make previous passes stale. Passing checks establish only their stated coverage.

`checker_run_checks` can execute only commands already approved by a human for the exact definition. Neither a plan nor this skill grants approval, and no MCP tool approves checks. If approval is missing, give the user the packaged human CLI command with the confirmed root, actual installed binary and retained state binding; do not guess those paths or feed its confirmation prompt yourself. For 0.4, keep Codex and the active writer open: the user runs the command in a separate interactive terminal, reviews the exact definition and types the confirmation. Approval does not execute the check; after confirmation, the same chat can request its run. Older frozen packages retain their own approval instructions. Use `checker_get_run` and bounded `checker_get_log` to explain failures.

Installation, tracking and service startup never run acceptance checks or create approvals. Source edits can stale passing evidence while leaving an unchanged grant reusable; accepted plan revisions invalidate execution grants. Cancelled confirmation, invalid challenges and changed bindings refuse approval. A transport or status error after confirmation can leave the exact grant saved; review a fresh approval if its outcome is unclear. Do not change private approval or evidence records to resolve an error.

If the checker is unavailable, continue normal Codex work and describe progress as unverified. Standard Codex exposes tools and this skill; the embedded progress panel is an optional feature of the maintained Codex fork.
